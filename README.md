# Цифровой механик

**От результата ML-диагностики — к понятному объяснению, проверке по заводскому руководству и заявке на дефектовку.**

Веб-прототип для механиков автопарков коммерческого транспорта и спецтехники, созданный для хакатона «ИИкузница» по кейсу «НейроДВС». Помощник связывает результат внешней диагностики с документацией конкретного двигателя и помогает довести обнаруженное отклонение до проверяемого действия.

Механику доступен весь рабочий путь в одном экране: выбрать машину и проверку, прочитать вердикт, задать вопрос, открыть нужную страницу руководства, проверить основание работ, отредактировать заключение и приоритет и получить номер ТОиР для разрешённого сценария.

> **Текущий статус:** работающий прототип на синтетическом парке и исходных Mock ML / Mock ТОиР заказчика. Поиск по шести оригинальным PDF реализован. По умолчанию работает демонстрационный режим без модели; `python run.py --agent` подключает встроенного Ollama-агента к чату и подготовке черновиков общего экрана. Также предусмотрено подключение внешнего агента. Реальная акустическая модель, производственная ТОиР и оценка диагностической точности в этот прототип не входят.

Сводка «Состояние парка» показывает категории, оценки пяти проверок и переход к записи. После диагностики доступна история машины. [Исследование интерфейсов](docs/gui-research.md)

- **Быстрый старт:** положить архив `007_хакатон_ИИ.zip` в корень и выполнить `docker compose up --build`.
- **Локальный экран:** [http://127.0.0.1:8000](http://127.0.0.1:8000/).
- **API основного экрана:** [Swagger UI](http://127.0.0.1:8000/api/docs).
- **Демонстрация:** [новый ролик F14, 20,56 секунды](<output/Цифровой механик — допуск.mp4>) · [сценарий и версия сборки](docs/Демо.md). Тестовый чат и исходные Mock-сервисы; живой LLM-прогон проверяется отдельно. [Старый ролик](<output/Цифровой механик — демо.mp4>) сохранён как история.

## Идея и ценность

Результат диагностики полезен, когда из него понятно, что делать дальше. Код отклонения, балл аномальности и уверенность модели сами по себе не объясняют механику условия проверки и не заполняют заявку на дефектовку.

«Цифровой механик» объединяет три источника: карточку транспортного средства, ответ ML-сервиса и заводское руководство. Такой подход помогает быстрее перейти от сигнала к проверке, сохранить обоснование решения и передать в ТОиР согласованные работы.

| Пользователь | Польза в рабочем процессе |
| --- | --- |
| Механик на посту | Краткий вердикт, первичная проверка, диалог и переход к конкретной странице PDF |
| Главный механик | Сохранённые результаты и заявки как основа будущей сводки по парку |
| Команда интеграции | Отдельные контракты ML и ТОиР, конфигурация адресов и воспроизводимый локальный стенд |

Бизнес-гипотеза проекта — сократить время на поиск процедуры и оформление дефектовки, а после подключения реальных данных помочь раньше замечать отклонения. Экономия на ремонтах и простое требует отдельного пилота с механиками; в прототипе она не измерена.

## Без решения и с решением

Сравниваем обычный процесс «получить результат ML → самостоятельно найти процедуру → заполнить ТОиР» с текущим прототипом. Это сравнение организации работы; исходный процесс конкретного автопарка ещё нужно измерить на пилоте.

| Этап | Без нашего решения | С нашим решением |
| --- | --- | --- |
| Получение отчёта | Отдельный просмотр результата ML и сопоставление с машиной | Выбор машины и записи запускает получение отчёта; сохранённый отчёт восстанавливается без повторного запроса ML |
| Поиск процедуры | Открытие подходящего руководства и самостоятельный поиск раздела | Поиск по применимой модели двигателя, карточка проверки и переход к нужной странице PDF |
| Нормы и условия | Механик сам сопоставляет значение, единицы, прогрев, обороты и исключения | Проверенная выдержка сохраняет условия вместе со значениями; недостающие факты уточняются в диалоге |
| Работа с результатом | Наблюдения записываются в выбранном на предприятии инструменте | Быстрые уточнения и ввод результата рядом с проверкой; механик проверяет текст перед отправкой |
| Заявка | Ручной перенос заключения, работ и ссылок | Редактируемый черновик по пригодным источникам; отправка только после подтверждения |
| Возврат к случаю | Зависит от журналов, документов и процессов автопарка | Диалог, результат, черновик и номер заявки сохраняются по машине и сессии |
| Ошибки записи и доставки | Требуют отдельного разбора оператором | Сбой записи отделён от неисправности двигателя; неизвестная доставка заявки имеет отдельный статус |
| Подтверждённое сокращение ремонта и простоя | Базовые данные отсутствуют | Пока не измерено: в наборе нет выполненных ремонтов и длительности простоя |

### Как оценивать возможный экономический эффект

Пример **гипотезы для пилота**, а не результат проекта: 1000 случаев в месяц, поиск и оформление сокращаются с 20 до 8 минут, полная стоимость часа механика — 600 ₽. Тогда высвобождается `1000 × (20 − 8) / 60 = 200 часов`, или **120 000 ₽ стоимости рабочего времени в месяц**. Это дополнительная производственная ёмкость; денежная экономия появится только при изменении оплачиваемых затрат или использовании этого времени с полезным результатом.

Из эффекта нужно вычесть инфраструктуру, сопровождение и амортизацию внедрения. При условном бюджете эксплуатации 25 000 ₽/мес порог покрытия составит `25 000 / ((20 − 8) / 60 × 600) ≈ 209 случаев/мес`. Если время не сократится, такого эффекта нет. Цены ремонта, предотвращённые поломки и простой в этот расчёт не включены.

## Что уже умеет прототип

- Выбирать ТС и диагностическую сессию из синтетического каталога: **50 машин и 195 проверок**.
- Автоматически получать ответ Mock ML при выборе новой для приложения пары ТС–сессия и различать **норму, отклонение и сбой записи**. Для уже проверенной пары восстанавливается сохранённый отчёт.
- Показывать тип отклонения, признаки, уверенность и качество записи; низкая уверенность и помехи отображаются отдельными предупреждениями.
- Искать фрагменты в руководствах с учётом модели двигателя и дополнительного контекста F01–F14.
- Открывать оригинальный PDF с номером страницы и отдельный PDF ровно одной страницы; для контрольных страниц есть изображения.
- Демонстрировать вопросы об условиях проверки, возможных причинах, нехватке данных и противоречии между кодом ML и двигателем.
- Готовить черновик только из серверных проверенных вариантов работ; заключение и приоритет проверяет и редактирует механик. Каждая работа связана с фрагментом, страницей и условиями.
- Отправлять разрешённую заявку в Mock ТОиР **после подтверждения приоритета и отдельного подтверждения warning**, если оно требуется; сохранять номер и восстанавливать его после обновления страницы.
- Защищать отправку от конкурентных дублей и устаревших изменений; отдельно обрабатывать неизвестный результат доставки.
- Сохранять диалог и технический журнал вызовов по выбранной машине и сессии.
- Работать в адаптивном интерфейсе; узкий экран проверялся в эмуляции Chromium.

Выбор машины и записи запускает отчёт. При ошибке запрос можно повторить. При переключении машины экран просит выбрать запись заново.

> **Согласование с кейсом:** в буквальном пункте F2 ТЗ v6 запуск описан отдельной кнопкой. Автоматический запуск при выборе записи — осознанное изменение UX по запросу команды; для приёмки это отличие нужно согласовать. Выбор ТС–сессии, отдельный вызов ML-инструмента и вывод вердикта в чат сохраняются. Это изменение не добавляет запись звука в браузере.

Обычный `run.py` запускает демонстрационный режим. Флаг `--agent` подключает встроенного агента через Ollama и сохраняет контекст выбранной записи. Работы в черновике проверяются по справочнику, а отправку в обоих режимах подтверждает механик.

## Быстрый запуск через Docker

### Что подготовить

1. Установите Docker с Compose; на Windows и macOS запустите Docker Desktop.
2. Получите выданный для кейса **внешний архив `007_хакатон_ИИ.zip`** и положите его рядом с `run.py` и `docker-compose.yml`.
3. Выполните команды из корня репозитория:

```bash
docker compose version
docker compose up --build
```

Откройте **[http://127.0.0.1:8000](http://127.0.0.1:8000/)** после сообщения о запуске сервера. Python, Poppler и зависимости устанавливаются в образе; локальная установка Python не нужна. Для стандартного демо не требуются `.env`, API-ключи или скачивание LLM.

При первом запуске приложение автоматически распакует руководства и заглушки, построит поисковый индекс и создаст предпросмотры. Дождитесь окончания подготовки: веб-сервер запускается после неё. Первый build требует сети для загрузки образа и пакетов; подготовленные исходные материалы используются локально.

В Compose один сервис `mechanic`: внутри контейнера штатный запуск поднимает экран и два локальных mock-сервиса. На компьютер опубликован только порт экрана; порты ML и ТОиР остаются внутри контейнера.

### Повторный запуск и сохранение данных

```bash
docker compose up -d
docker compose logs -f mechanic
docker compose down
```

`up -d` запускает стенд в фоне. `logs -f` показывает подготовку и ошибки. `down` останавливает стенд и удаляет контейнер, сохраняя папку `artifacts` на компьютере.

- `./artifacts` подключена в `/app/artifacts` с правом записи: здесь сохраняются PDF, индекс, предпросмотры и SQLite.
- Корень проекта подключён в `/input` только для чтения, чтобы контейнер мог найти исходный архив.
- Архив, локальные базы, `.env` и материалы заказчика не копируются в Docker-образ.
- После изменения кода используйте `docker compose up --build`; после изменения только конфигурации достаточно пересоздания контейнера.

Если порт занят, создайте корневой `.env` с одной строкой и повторите запуск:

```dotenv
APP_PORT=8015
```

Экран будет доступен по адресу [http://127.0.0.1:8015](http://127.0.0.1:8015/). По умолчанию Compose публикует его только на `127.0.0.1`. Это конфигурация локального стенда; для публичного размещения потребуются отдельные настройки доступа и эксплуатации.

## Локальный запуск

### Требования

- Рекомендуется **Python 3.13**.
- Poppler: утилиты `pdftotext` и `pdftoppm` должны быть доступны в `PATH`.
- Выданный заказчиком архив `007_хакатон_ИИ.zip` в корне проекта.
- Доступ в сеть при установке Python-пакетов.

### Windows и PowerShell

Установите Python. Для Poppler скачайте сборку из [репозитория Windows-пакета](https://github.com/oschwartz10612/poppler-windows/releases), распакуйте её и добавьте каталог с `pdftotext.exe` и `pdftoppm.exe` в `PATH` — обычно это `Library\bin`. Откройте новый PowerShell и проверьте:

```powershell
py -3.13 --version
pdftotext -v
pdftoppm -v
```

Из корня проекта, где уже лежит архив:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

Активировать виртуальное окружение или менять политику выполнения PowerShell не требуется. Для повторного запуска достаточно последней команды.

[Открыть рабочий экран](http://127.0.0.1:8000/). Для отдельного API и заглушек используется `main.py`. [Swagger UI](http://127.0.0.1:8000/docs)

### macOS

Установите Python 3.13 и Poppler, например через Homebrew:

```bash
brew install python@3.13 poppler
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python run.py
```

### Linux

Установите Python 3.13 с поддержкой `venv`. Для Debian/Ubuntu установите Poppler командой:

```bash
sudo apt-get update
sudo apt-get install poppler-utils
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python run.py
```

Если подходящий Python недоступен в дистрибутиве, используйте Docker. После старта откройте [http://127.0.0.1:8000](http://127.0.0.1:8000/). Остановка — `Ctrl+C`; запущенные этим процессом заглушки также останавливаются.

### Встроенный агент через Ollama

Запустите Ollama отдельно, загрузите модель и включите агента в общем экране:

```bash
ollama pull gemma2:2b
python run.py --agent
```

Используйте Python виртуального окружения, как в командах выше. `--agent` совместим с `--archive`, `--rebuild-index` и `--no-mocks`. Модель задаёт `AGENT_MODEL`, адрес Ollama — `OLLAMA_HOST_URL`. При недоступной Ollama или отсутствующей модели чат покажет ошибку; демонстрационный режим запускается обычной командой `python run.py`.

Для формулировки ответа по выбранным выдержкам загрузите `qwen3.5:9b` на сервере Ollama и задайте `OLLAMA_GENERATION_MODEL=qwen3.5:9b`. При сбое генерации экран показывает найденные выдержки со ссылками.

В Docker сначала загрузите модель в Ollama на компьютере, затем добавьте в корневой `.env`:

```dotenv
CASE_AGENT=1
AGENT_MODEL=gemma2:2b
```

Запустите `docker compose up --build`. Compose обращается к Ollama на компьютере через `host.docker.internal:11434`; для другого сервера задайте `OLLAMA_HOST_URL`. Ollama и модель не включены в образ приложения.

### Проверка с телефона

Для локального прогона в одной сети запустите:

```bash
.venv/bin/python run.py --host 0.0.0.0 --port 8015
```

На Windows замените `.venv/bin/python` на `.\.venv\Scripts\python.exe`. Откройте на телефоне `http://<IP-компьютера>:8015/`; доступ может потребовать разрешения в локальном брандмауэре. Актуальный чек-лист — в [приёмке серверного допуска](docs/Приёмка-допуска.md). Проверка на физическом смартфоне пока не выполнена; эмуляция браузера её не заменяет. [Предыдущая приёмка](docs/Приёмка.md) сохранена как исторический документ.

## Автоматическая подготовка материалов

Для обычного запуска **не нужно вручную распаковывать архив или отдельно строить индекс**. `run.py` выполняет подготовку до запуска сервисов:

1. Находит архив в корне проекта либо использует явно указанный путь.
2. Извлекает шесть руководств и вложенный архив `neurodvs_hackathon_mock_2026-11-16.zip` с Mock ML и Mock ТОиР.
3. Проверяет необходимые файлы и средства извлечения PDF.
4. Строит `artifacts/manual-corpus.json` с привязкой фрагментов к страницам и моделям двигателей.
5. Создаёт предпросмотры контрольных страниц и сохраняет сведения о подготовке.
6. При следующем запуске использует совместимые подготовленные результаты; при необходимости обновляет их.

Совместимость проверяется по содержимому исходных файлов, разметки и кода подготовки. Изменённый PDF или повреждённый индекс вызывают пересборку; перенос между локальным запуском и Docker сам по себе её не требует. Индекс заменяется атомарно после успешной обработки PDF и предпросмотров.

Нужен полный внешний архив с руководствами и вложенными заглушками. Один архив `neurodvs_hackathon_mock_2026-11-16.zip` содержит только заглушки и не заменяет комплект материалов. Документы с описанием кейса не используются как технический источник ответов.

### Другой путь или имя архива

```bash
python run.py --archive "/путь/к/007_хакатон_ИИ.zip"
```

По умолчанию материалы ищутся рядом с `run.py`, независимо от текущего каталога терминала. Поддерживаются `007_хакатон_ИИ.zip`, распакованная папка `007_хакатон_ИИ/` или шесть PDF и `neurodvs_hackathon_mock_2026-11-16.zip` прямо в корне. Внешний ZIP имеет приоритет. Указывать `--archive` для стандартного расположения не нужно. Уже подготовленные полные материалы в `artifacts` используются повторно.

Можно задать `CUSTOMER_ARCHIVE_PATH` в `.env`: это путь к ZIP либо каталогу для поиска архива. В Docker эта переменная указывает на `/input`; проще оставить архив в корне проекта. В командах этого раздела `python` означает интерпретатор установленного виртуального окружения.

Каталог `data/vehicles.json` содержит **50 синтетических ТС и 195 сессий**: 111 нормальных, 69 с отклонением и 15 сбоев записи. Модель двигателя заполнена у всех машин; модель автомобиля у части записей отсутствует. Типы F01–F14 — условные коды Mock ML, а не обозначения из руководств.

| ЯМЗ-536 | Эксплуатация 536.3902150 РЭ; ремонт 536.01.02 РК | 285 + 603 |

Корпус текущего комплекта содержит около **10 тысяч фрагментов**. Каждый фрагмент хранит документ, порядковую страницу PDF, текст, раздел и применимые модели. Дополнительно есть вручную проверенные выдержки, словарь поисковых терминов и карты первичных проверок. Точные файлы и номера страниц описаны в [документации поиска](docs/manual-search.md).

На 40 страницах отмечен пустой или скудный текстовый слой; часть таких страниц — обложки и рисунки, часть — таблицы, требующие OCR или ручной разметки. Количество фрагментов не является метрикой полноты знаний.

Реальные аудиозаписи, подтверждённые дефекты, результаты ремонта, стоимость работ и длительность простоя в наборе отсутствуют. `confidence` и `anomaly_score` показываются как поля ответа ML; их калибровка на реальном парке не проверялась.

Материалы заказчика, SQLite и производные файлы находятся в `artifacts` и исключены из Git. Исходный архив нужно получить отдельно; он не скачивается приложением автоматически и не включается в образ.

## Архитектура и текущий RAG

```text
Карточка ТС + выбранная сессия
            │
            ▼
       Mock ML API ──► статус, код, признаки, оценки, качество
            │
            ▼
  Workflow + поиск по руководствам
            │
            ├──► фрагменты применимой модификации + ссылки на страницы
            │
            ▼
  Основной экран: вердикт, диалог, проверяемый черновик
            │
            ▼
    Подтверждение механика ──► Mock ТОиР ──► ticket_id
```

**Стек:** Python, FastAPI, Pydantic, HTTPX, Uvicorn, SQLite; HTML/CSS/JavaScript; Poppler и pypdf для PDF; Docker Compose для воспроизводимого запуска. Для стандартного демонстрационного режима не требуется отдельная СУБД или сервер LLM.

### Что реализовано в поиске

`manual_search` извлекает текст PDF через Poppler, строит фрагменты и ранжирует их по словам, синонимам и предметным признакам. Модель двигателя ограничивает кандидатов; код отклонения дополняет контекст запроса. В корпусе сохраняются связи продолжения фрагментов и отдельная разметка применимости общего руководства ЗМЗ.

Сервер разрешает идентификатор найденного фрагмента в документ и страницу, проверяя модификацию. Ссылки ведут на порядковые страницы исходного PDF. Векторная база и эмбеддинги в текущем поиске не используются.

### Что реализовано в агенте

В основном экране `run.py` → `mechanic.main` по умолчанию работает демонстрационный диалог. При заданном `TEAM_AGENT_URL` приложение передаёт внешнему агенту контекст машины, ответ ML, историю и найденных кандидатов источников через `POST /respond`. Ответ проверяется по схеме и допустимым источникам.

Флаг `--agent` или `CASE_AGENT=1` подключает встроенный `CaseAgent` к карточке диагностики, чату и подготовке черновиков. Он использует поиск по применимым руководствам и сохраняет контекст уточнений в SQLite по машине и сессии. Журнал реплик находится в `artifacts/agent-turns.jsonl`. Сбой записи и противоречащий двигателю код обрабатываются до вызова модели. При заданных `TEAM_API_URL` или `TEAM_AGENT_URL` приоритет имеет внешняя интеграция.

Отдельный `main.py` запускает `backend.app`: в нём есть Ollama-маршрутизатор инструментов, а технические ответы формируются правилами и извлечёнными выдержками. Этот обработчик чата автоматически не подменяет диалог основного экрана. Простая установка `OLLAMA_MODEL` не превращает основной экран в свободный LLM-чат.

База знаний, поиск и встроенный диалог уже соединены в общем экране в режиме `--agent`. Дальнейшая работа — расширение объяснений, улучшение поиска и независимая проверка качества ответов. Проверка допустимости ссылки сама по себе не доказывает, что каждое написанное утверждение следует из её содержания.

Контракты и детали — в [документе интеграции](docs/Интеграция.md), [описании backend](docs/backend.md) и [документации агента](docs/agent/README.md). Отдельный Flask-стенд из документации агента — дополнительный способ запуска; для общего экрана он не требуется.

Для ЯМЗ-536 добавлена сверенная выдержка PDF 49 с условиями прогрева, режимами, значениями и единицами давления масла. Одинаковый абзац одного источника выводится один раз; разные полезные абзацы сохраняются.

## Серверный допуск и доказательства

Допуск вычисляется в одном месте перед подготовкой и ещё раз перед отправкой. Сервер читает последнюю сохранённую диагностику, двигатель карточки ТС и реестр проверенных работ. UI показывает `can_prepare`, `can_submit`, причину `block_reason`, необходимость отдельного подтверждения warning, версию диагностики и ревизию черновика.

- `bad` / `check_failed` требуют новой записи и не дают заключения о состоянии двигателя.
- Уверенность **ниже 0,50** закрывает отправку; на значении 0,50 действуют остальные проверки. `warning` показывается всегда, в том числе при низкой уверенности, и подтверждается отдельно от приоритета.
- Несовместимый F-код блокируется по карточке двигателя; исходный ответ ML сохраняется для объяснения.
- Каждая работа связана с точным проверенным фрагментом, узлом и условиями. Страница того же двигателя про другой узел не подтверждает работу. Заключение и приоритет редактируются, список работ ограничен проверенными вариантами.
- Изменение результата, качества или уверенности делает старую версию подтверждения неактуальной. Откройте свежий отчёт и снова проверьте подтверждения.

Три размеченных конфликта показываются с обеими сторонами: клапаны РЭ PDF 31 / РК 269, 276; масло РЭ PDF 19 / РК 12; коренные опоры РК PDF 41 / 248. Условия и расхождения не усредняются. Для клапанов правило «на холодном двигателе» явно обозначено как согласованное правило демо. Высокий приоритет — организационная рекомендация по дефектовке, а не прямой запрет движения из руководства.

Подробности: [API допуска](docs/admission-api.md) · [доказательства и вопросы QA](docs/manual-evidence.md) · [приёмка и физический телефон](docs/Приёмка-допуска.md) · [живой агент и журнал](docs/agent/acceptance-runs.md).

## Надёжность заявок

Заявка содержит пару ТС–сессия, код отклонения, заключение, приоритет, работы, запчасти и ссылки. Механик проверяет содержимое до отправки и редактирует заключение и приоритет. Работы и их источники задаются проверенным вариантом; список запчастей может быть пустым, если детали не определены.

- `revision` защищает от сохранения и подтверждения устаревшего черновика.
- Текущий черновик выбирается по машине, сессии и коду последней диагностики. После смены кода старый остаётся в backend-истории, а новый создаётся отдельно.
- SQLite атомарно резервирует отправку и сохраняет номер принятой заявки.
- Повторное подтверждение успешно отправленной заявки возвращает сохранённый номер.
- При определённой ошибке доставки сохраняется черновик для исправления и ручного повтора.
- При неизвестном результате отправки новый POST блокируется: заявка могла уже попасть в ТОиР. Предусмотрена ручная сверка номера и его сохранение.

Mock ТОиР хранит собственные заявки в памяти. После его перезапуска нумерация может начаться заново; локально сохранённые номера остаются в SQLite. Заглушка не предоставляет API для автоматической сверки неизвестной доставки. Это ограничение mock-контракта.

## Модель, сервер и стоимость эксплуатации

**Для первого пилота предлагаем один сервер с 8 vCPU, 16 ГБ RAM и 80 ГБ SSD, локальную Ollama и `gemma2:2b`. Плановый бюджет — около 13 000 ₽/мес за инфраструктуру или 19 000–25 000 ₽/мес с оговорённым ниже резервом на сопровождение.** GPU для такого старта не является обязательным. Это расчёт ресурсов для проверки, а не подтверждённая производительность облачного сервера.

### Где нужна модель

- Демонстрация `python run.py` работает без LLM и без платы за токены.
- В `python run.py --agent` модель нужна для выбора действия в диалоге и фрагментов для ответа/черновика; поиск по PDF и интеграции ML/ТОиР остаются отдельными инструментами. Саму акустическую диагностику эта LLM не выполняет.
- Ollama запускается отдельно от контейнера приложения. При локальной модели нет счёта внешнего API за каждый токен; остаются затраты на сервер, электричество и обслуживание.

| Вариант | Ресурсы для первого прогона — оценка команды | Для чего подходит |
| --- | --- | --- |
| Демо без модели или приложение с отдельным LLM-сервером | 2–4 vCPU, 4–8 ГБ RAM, 40–80 ГБ SSD | UI, API, текущий индекс, SQLite и исходные mock-сервисы |
| Текущий агент `gemma2:2b` на одном CPU-сервере | **8 vCPU, 16 ГБ RAM, 80 ГБ SSD**, сначала один активный запрос к модели | Небольшой пилот без покупки GPU; требуется проверить задержку на выбранном процессоре |
| Та же модель на имеющемся компьютере | Современный CPU/Apple Silicon, желательно 16 ГБ RAM и 20 ГБ свободного места | Самый дешёвый способ проверить полезность с одним постом |
| Испытание более крупной модели | Кандидат `qwen2.5:7b` в 4-битном виде; 32 ГБ RAM, GPU с 12–16 ГБ VRAM как стартовая оценка | Эксперимент на сложных формулировках, а не автоматическая замена прошедшего проверку агента |

В [каталоге Ollama `gemma2:2b`](https://ollama.com/library/gemma2:2b) указан пакет Q4_0 размером около **1,6 ГБ**; для [`qwen2.5:7b`](https://ollama.com/library/qwen2.5:7b) — Q4_K_M около **4,7 ГБ**. Размер весов на диске **не равен** необходимой RAM/VRAM: память нужна также контексту, вычислениям, ОС и приложению. Требования в таблице включают запас, но ещё не подтверждены нагрузочным тестом. По [документации Ollama](https://docs.ollama.com/faq) размещение модели на CPU/GPU можно проверить командой `ollama ps`; увеличение контекста и параллельных запросов требует дополнительной памяти.

Не нужен отдельный GPU на каждого механика: модель может обслуживать общий сервер, но допустимое число одновременных диалогов предстоит измерить. Для текущих шести PDF не требуются отдельная векторная БД, Kubernetes и обучение модели с нуля. SSD закладывается с запасом под ОС, Docker, PDF, индекс, модели и рост журналов; внешние резервные копии хранятся отдельно.

### Сколько стоит месяц

Расчёт подготовлен **27 ноября 2026 года** по открытым страницам провайдеров. Это ориентир для бюджета, не коммерческое предложение и не средняя цена рынка. Везде, где используется почасовой тариф, условный месяц — **730 часов**; фактический счёт зависит от календаря, региона и конфигурации.

Для примера CPU-варианта использованы опубликованные в [правилах Yandex Compute Cloud](https://yandex.cloud/ru/docs/compute/pricing) ставки примера Intel Ice Lake: 1,24 ₽ за час vCPU с уровнем 100% и 0,33 ₽ за ГБ RAM в час, с НДС. Тогда вычисления 4 vCPU / 8 ГБ стоят `730 × (4 × 1,24 + 8 × 0,33) = 5548 ₽`, а 8 vCPU / 16 ГБ — `11 096 ₽`. Диск, IP, снимки и трафик оплачиваются отдельно; **2000 ₽ ниже — наш плановый резерв на эти статьи, а не тариф провайдера**. Перед заказом нужен расчёт нужной конфигурации в актуальном калькуляторе.

| Сценарий | Расчёт | Плановый расход в месяц |
| --- | --- | ---: |
| Существующий компьютер + локальная Gemma 2 2B | Дополнительная аренда и внешний токенный API — 0 ₽ | **0 ₽ аренды**, плюс электричество, резервные копии, обслуживание и износ оборудования |
| Веб-приложение 4 vCPU / 8 ГБ, модель на уже имеющемся отдельном компьютере | 5548 ₽ вычисления + резерв 2000 ₽ | **Около 7500 ₽**, плюс эксплуатация компьютера с моделью |
| Всё на CPU-сервере 8 vCPU / 16 ГБ | 11 096 ₽ вычисления + резерв 2000 ₽ | **Около 13 100 ₽** |
| Всё на GPU-сервере, постоянно | L4 24 ГБ + 8 vCPU + 32 ГБ RAM: от 69,88 ₽/ч × 730 = 51 012,40 ₽; резерв 2000 ₽ | **От 53 000 ₽**; для небольшой Gemma 2 это избыточный стартовый вариант |
| GPU только на тестовые интервалы | Тот же тариф × 50 оплачиваемых часов = 3494 ₽ | **От 3494 ₽ за вычисления**, плюс постоянный веб-сервер и хранение ресурсов между интервалами |

GPU-пример взят из [официальной конфигурации Selectel](https://selectel.ru/services/gpu/); ставка указана как «от», состав дисков и итоговые налоги нужно проверить при заказе. Почасовой вариант предполагает управление платными ресурсами по правилам провайдера: простая остановка процесса Ollama не прекращает аренду. Автоматическое включение/выключение GPU в проекте пока не реализовано.

**Эксплуатация шире аренды:** для финансового плана можно заложить 4–8 часов сопровождения в месяц по условной внутренней ставке 1500 ₽/ч, то есть ещё **6000–12 000 ₽**. Это допущение команды на обновления, разбор ошибок, контроль источников и резервных копий, а не рыночная котировка. Расширение каталога руководств и двигателей потребует отдельной оценки. Получается около **19 000–25 000 ₽/мес** для CPU-пилота или от **59 000–65 000 ₽/мес** с постоянной L4. При нагрузке 1000 случаев/мес CPU-инфраструктура соответствует примерно 13 ₽/случай, а с таким сопровождением — 19–25 ₽/случай; это распределение бюджета, не токенный тариф.

В сумму не включены разработка и внедрение, промышленная акустическая ML-модель, лицензии/интеграция рабочей ТОиР, устройства записи, выделенный интернет, домен, отказоустойчивый дубль и специальная поддержка. Потребность в этих статьях зависит от предприятия. Пример относится к текущему прототипу с Mock ML/ТОиР, а не к полной цене промышленного продукта.

### Если модель вынести в платный API

Внутри основного агента реализован протокол Ollama; произвольный API с оплатой за токены не подключается одной заменой `OLLAMA_HOST_URL`. Для него нужен адаптер провайдера либо внешний агент через `TEAM_AGENT_URL` с контрактом `/respond` и сохранением проверок источников.

Для предварительного сравнения можно взять **только объём** исторического локального прохода: 3160 входных и 349 выходных токенов на цикл. При 1000 таких циклов/месяц получится 3,16 млн входных и 0,349 млн выходных токенов:

```text
LLM в месяц = 3,16 × цена 1 млн входных токенов
            + 0,349 × цена 1 млн выходных токенов
```

Например, при **условных**, не взятых у провайдера ставках 100 и 300 ₽ за миллион это 420,70 ₽/мес только за генерацию. К этому добавятся веб-сервер, иные платные операции и сопровождение. История, повторы, новые вопросы, другая токенизация и модель изменят объём; перед выбором API нужен новый журнал полного цикла, а не умножение цены одной реплики.

### Когда увеличивать инфраструктуру

Начните с одного поста и измеряйте холодный/прогретый запуск, p50/p95 полного ответа, очередь, расход RAM/VRAM, ошибки, число вызовов и токены. В локальном замере использовался MacBook M3; его секунды нельзя обещать на CPU VPS. Проверяйте совместимость с текущими тайм-аутами приложения и повышайте ресурсы только после такого прогона. Если очередь мешает работе, сначала сравните GPU и более компактные запросы; при росте парка — вынесите модель, добавьте очередь и оцените переход с SQLite на серверную БД. Эти шаги масштабирования пока не реализованы.

## Проверка качества

Итоговый общий прогон 27.11.2026: **116 тестов и 207 дополнительных проверок прошли**, пропусков нет; 104,25 с. [Журнал](output/admission-pytest.log), [состав сборки](output/admission-build.json), [матрица API и браузера](docs/Приёмка-допуска.md). Временное окружение проверки включало необязательный Flask для теста закрытого старого маршрута отправки.

Установите зависимости для разработки в виртуальное окружение:

```bash
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -p test_prepare.py -v
python -m unittest discover -s tests -p test_backend.py -v
python -m pytest tests/test_mechanic.py -q
```

Здесь и далее используйте `.venv/bin/python` на macOS/Linux либо `.\.venv\Scripts\python.exe` на Windows, если окружение не активировано. Перед интеграционными тестами подготовьте материалы командой `python -m mechanic.prepare`.

Проверка корпуса и контрольных поисковых запросов на macOS/Linux:

```bash
PYTHONPATH=. .venv/bin/python tests/check_manual_search.py artifacts/manual-corpus.json
```

В PowerShell:

```powershell
$env:PYTHONPATH = "."
.\.venv\Scripts\python.exe tests/check_manual_search.py artifacts/manual-corpus.json
```

Тесты backend проверяют исходные ASGI-приложения заказчика через тестовый транспорт: три исхода диагностики, неверные пары, ошибки внешних сервисов, ревизии, конкурентное подтверждение и неизвестную доставку. Для проверки поиска предусмотрены 13 запросов; ещё два сценария проверяются через чат.

Автоподготовка проверяется отдельно: отсутствие и повреждение архива, отсутствие Poppler, кеширование, изменение PDF, повреждение индекса, перенос подготовленных материалов, принудительная пересборка и сохранность прежнего индекса при сбое. Контейнерная проверка прошла путь от распаковки шести PDF и заглушек до ответа с источниками и подтверждённой заявки; повторный запуск использовал кеш, номер заявки сохранился после пересоздания контейнера.

**Граница этих проверок:** прохождение фиксированных вопросов не доказывает качество на новых формулировках. Часть запросов использовалась при настройке поиска. Нужен независимый набор перефразировок, многоходовых диалогов, вопросов без ответа и проверок технических утверждений. Тестовый режим также не доказывает работу внешнего LLM-агента.

Дополнительная браузерная приёмка доступна в `tests/browser_check.py`. Она требует локального `.venv`, Playwright и установленного Chromium; запускает временные базы и HTTP-стенд. Подготовка и запуск:

```bash
python -m pip install playwright
python -m playwright install chromium
python tests/browser_check.py --expect-team
```

Перед прогоном должен работать локальный стенд с Mock ML / ТОиР, например запущенный в другом терминале через `run.py`. Результаты сохраняются в `.runtime/qa`. Исторические результаты сохранены в [прежней приёмке](docs/Приёмка.md). Актуальная матрица допуска и незавершённая проверка физического телефона — в [приёмке допуска](docs/Приёмка-допуска.md).

В [документе демо](docs/Демо.md) сохранено историческое сравнение автоматизированных проходов Chromium на двух сценариях до усиления допуска. Это замер действий скрипта, а не рабочего времени механика. Он не подтверждает экономию труда, реальную диагностическую точность или стоимость текущего LLM-цикла. Новый живой прогон пока не выполнен: локальная Ollama недоступна; точный статус и воспроизводимая команда находятся в [журнале приёмки агента](docs/agent/acceptance-runs.md).

## Идеи развития

Следующие пункты — **план**, а не описание уже готовых возможностей. Приоритет — повысить достоверность и проверить пользу на одном посту; новые роли и масштабирование идут после устойчивого основного сценария.

| Направление | Следующий шаг | Как проверить результат |
| --- | --- | --- |
| Единый агент | Расширить подключённый агент на начальное объяснение диагностики и унифицировать контракты | Сквозные сценарии со свободными формулировками и измерение качества всего пути |
| Память случая | Хранить измерения с единицами, оборотами и прогревом, факты, гипотезы и недостающие условия | Многоходовой диалог без потери фактов и повторных вопросов |
| Поиск по руководствам | Сохранять таблицы с заголовками и сносками, обработать проблемные страницы, сравнить лексический и гибридный поиск | Независимые запросы, попадание в нужные источники и корректный отказ |
| Проверка обоснования | Связать каждое техническое утверждение и операцию с фрагментами и условиями применимости | Правильность чисел, модификаций и подтверждение выводов источниками |
| История ТС | Использовать прошлые проверки и заявки; добавить график `anomaly_score` | Правильная привязка к машине и версии модели, отдельное отображение пропусков |
| Главный механик | Сводка по парку и список требующих внимания случаев | Согласованные правила категорий и переход к обоснованию каждого случая |
| Реальные интеграции | Подключить рабочий ML API и ТОиР, добавить идентификатор идемпотентности и сверку доставки | Контрактные тесты, отсутствие дублей и восстановление после сбоев |
| Обратная связь | Сохранять подтверждённый дефект, измерения, исправления механика и итог ремонта | Оценка качества на подтверждённых исходах |
| Модели и инфраструктура | Сравнить текущую Gemma 2 2B, более крупного локального кандидата и API на одном независимом наборе | Качество с подтверждением источников, p95, стоимость полного случая и пиковая память |
| Пилот | Сравнить ручной процесс и помощника у 5–7 механиков с чередованием одинаковых случаев | Время до проверенного черновика, исправления, пропуски условий, успешные заявки и фактический бюджет |
| Продукт для предприятия | Авторизация и роли, резервные копии с восстановлением, мониторинг и согласованное хранение данных | Проверенный доступ, восстановление, наблюдаемость сбоев и стоимость сопровождения |

Базовая архитектурная гипотеза — один ведущий агент с инструментами и проверками в коде. Дополнительного агента имеет смысл испытывать на независимом поиске или проверке сложных ответов. Решение о мультиагентности следует принимать по качеству, задержке и стоимости на одинаковых сценариях.

До публичной эксплуатации также нужны аутентификация, разграничение доступа, управление секретами, резервное копирование и эксплуатационный мониторинг. Текущая локальная сборка этих свойств не заявляет.

## Команды и структура проекта

| Команда | Назначение |
| --- | --- |
| `docker compose up --build` | Собрать образ, автоматически подготовить материалы и запустить стенд |
| `docker compose logs -f mechanic` | Посмотреть подготовку и работу контейнера |
| `docker compose down` | Остановить контейнер, сохранив локальный `artifacts` |
| `python run.py` | Подготовить и запустить экран, Mock ML и Mock ТОиР локально |
| `python run.py --agent` | Подготовить материалы и включить встроенный чат через запущенную Ollama |
| `python run.py --archive <ZIP>` | Запустить с явно указанным архивом |
| `python run.py --rebuild-index` | Пересобрать производные данные и запустить стенд |
| `python run.py --no-mocks` | Использовать уже работающие внешние сервисы |
| `python -m mechanic.prepare` | Подготовить материалы без запуска HTTP-сервисов |
| `python -m mechanic.prepare --rebuild` | Принудительно пересобрать индекс и предпросмотры |
| `python main.py` | Запустить отдельный backend API и две заглушки |

```text
.
├── run.py                    # Основной запуск с автоматической подготовкой
├── main.py                   # Отдельный backend API
├── Dockerfile                # Python, Poppler и зависимости приложения
├── docker-compose.yml        # Локальный контейнер и сохранение artifacts
├── requirements.txt          # Зависимости приложения
├── requirements-dev.txt      # Дополнительные зависимости тестов
├── mechanic/                 # Экранный API, состояние, адаптеры и подготовка
├── backend/                  # Workflow диагностики, черновиков и ТОиР
├── manual_search/            # Извлечение PDF, индекс и поиск
├── data/                     # Синтетический каталог и разметка знаний
├── contracts/                # OpenAPI Mock ML и Mock ТОиР
├── web/                      # HTML, JavaScript и стили
├── tests/                    # Backend, поиск, интерфейс и замеры
├── docs/                     # Интеграция, приёмка, аудит и демо
├── output/                   # Демонстрационный ролик
├── 007_хакатон_ИИ.zip         # Получается отдельно; исключён из Git
└── artifacts/                # Создаётся автоматически; исключён из Git
    ├── customer/             # Исходные mock-приложения заказчика
    ├── manuals/              # Шесть PDF
    ├── manual-corpus.json    # Поисковый индекс
    ├── manual-previews/      # Изображения контрольных страниц
    ├── mechanic.sqlite3      # Диагностики и заявки
    └── mechanic-assistant.sqlite3  # Диалог и журнал
```

Подробности: [поиск по руководствам](docs/manual-search.md) · [backend](docs/backend.md) · [интеграция](docs/Интеграция.md) · [приёмка](docs/Приёмка.md) · [аудит](docs/audit.md) · [демо](docs/Демо.md).
