# Допуск заявки на сервере

Правило находится в `backend/admission.py` и применяется при подготовке и фактическом подтверждении заявки. Реестр допустимых работ — `data/manuals/approved-operations.json`. Работа связана с точным ID фрагмента, двигателем, F-кодом, узлом, дословным текстом и условиями применения. Одного существования страницы нужного двигателя недостаточно.

## Решение API

`POST /api/diagnose`, `GET /api/admission?vehicle_id=…&session_id=…` и `DraftView.admission` возвращают:

```json
{
  "can_prepare": true,
  "can_submit": false,
  "block_reason": {
    "code": "warning_ack_required",
    "message": "Запись с помехами. Нужно отдельное подтверждение предупреждения.",
    "next_action": "Прочитайте предупреждение о качестве записи и явно подтвердите продолжение."
  },
  "warning_ack_required": true,
  "diagnosis_revision": "sha256-последней-сохранённой-диагностики",
  "draft_id": "id-черновика",
  "draft_revision": 1,
  "suggested_urgency": "medium",
  "approved_operations": []
}
```

В реальном ответе `approved_operations` содержит применимые серверные варианты: `id`, `operation`, `node`, `engine_model`, `anomaly_type`, `fragment_id`, `manual`, `pdf_page`, `quote`, `conditions`, `references`, `evidence`. Для каждой дополнительной страницы условия в `evidence` есть точный текст и `source` с ID, документом, PDF-страницей и ссылкой. В приведённом примере массив сокращён только для читаемости документа.

`can_prepare` разрешает открыть проверенный черновик даже при ещё не подтверждённом условии применения. `can_submit` учитывает содержимое и явные подтверждения, переданные в вычисление решения. Без черновика оно `false`; подтверждение warning и подтверждение приоритета независимы. При ошибке бизнес-правила тело ответа содержит `error` и `admission`, при наличии также `draft`.

## Внутренний запрос подтверждения

```json
{
  "revision": 1,
  "diagnosis_revision": "sha256-из-актуального-admission",
  "urgency": "medium",
  "confirmed": true,
  "warning_acknowledged": true,
  "applicability_confirmations": ["initial_start_or_long_storage"]
}
```

`confirmed` подтверждает выбранный приоритет; `warning_acknowledged` — предупреждение о записи. Для `warning` нужен актуальный `diagnosis_revision`. `applicability_confirmations` содержит ID только тех фактических условий, которые механик явно подтвердил. Для F08 ЯМЗ-236М2 это подготовка к первичному пуску или пуску после длительной стоянки. Условие можно сохранить в `PATCH /api/drafts/{id}`. Оно хранится отдельно от внешнего JSON заявки.

В Mock ТОиР по-прежнему уходят только поля заказчика: машина, сессия, код, заключение, приоритет, работы, запчасти, ссылки. Флаги, хеш диагностики и ID фрагментов не добавляются к этому контракту.

## Правила и версии

- `bad` / `check_failed`: повторная запись, заключение о двигателе отсутствует, заявки нет.
- `confidence < 0.50`: блокировка; `0.50` проходит порог и проверяет остальные условия.
- Несовместимый F-код сверяется с двигателем и топливом карточки ТС. Исходный код ML сохраняется для объяснения.
- Работы и ссылки должны совпадать с серверным проверенным вариантом. Заключение и выбранный приоритет остаются редактируемыми.
- Изменение сохранённой диагностики, включая качество и уверенность при прежнем F-коде, повышает ревизию редактируемого черновика и сбрасывает подтверждённые условия/приоритет. Старый запрос подтверждения получает `409 stale_draft`.
- Сервер предлагает `high` для F02 и `medium` для прочих случаев. `anomaly_score` не меняет приоритет. Для F02 ЯМЗ-236М2 разрешена первичная проверка уровней по PDF 53 РЭ. Замер контрольным манометром в перечень работ допуска не входит.
- Повтор подтверждения отправленной заявки возвращает тот же `ticket_id`. Неизвестная доставка блокирует новый POST и требует ручной сверки.

Старые редактируемые черновики без хеша диагностики при наличии разрешённого сценария получают проверенные работы и источники с повышением ревизии. Заключение, выбранный приоритет и запчасти сохраняются. Старые отправленные заявки не изменяются.

